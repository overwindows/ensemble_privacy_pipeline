Gemma 4 26B-A4B: Closing the MoE Weight-Bandwidth Wall
from 2045 to 2634 TPS, Toward 3000

Chen Wu · Q:\agentic_vllm + vllm-msn-s2 fork · loading…
Abstract. On a single A100 80GB (sm_80) we push offline gemma-4-26B-A4B MoE serving from a previous best 2045.7 output tokens/s to 2634.58 at the true S2 8192-token decode — crossing the original 2500 target by ~5% — through a decode-2D tile/stage geometry plus a DSpark b16 draft swap that raises accepted-token throughput over the stock Google MTP-assistant draft (+3.8% at a matched 768-token decode, TPS and QPS). The model is now weight-HBM-bound in the FP8-Marlin GEMM (~53% of step time); the remaining levers are (i) an int5 / int4 W4A16 weight compression (halving weight bytes/HBM) and (ii) further decode-side parallelism, which together are the planned route to 3000 output TPS. Because weight-precision is a quality change, acceptance is gated behind an agentic tool-loop + GSM8K/BBH quality A/B (within noise of the FP8 control, <1–2% absolute per benchmark). This page is the live results post of that campaign and tracks the 3000 push.

2  Introduction

The campaign objective is a single-worker 3000 output tokens/s on Gemma-4-26B-A4B-it MoE on an A100 80GB. Prior work (this series) established a decode-2D tile/stage geometry (S2, D2G TILE=32 / STAGES=2 / WARPS=0) that lifted throughput to ~2403–2429 output TPS. Swapping the speculative draft from the Google MTP-assistant to a DSpark b16 draft then crossed the earlier 2500 milestone: 2634.58 output TPS at the true S2 8192-token decode. Today the model is weight-HBM-bound in the FP8-Marlin GEMM (~53% of step time) — a wall the decode geometry alone cannot clear. Reaching 3000 (~+14% over the current best) therefore needs two orthogonal levers: (i) shrink weight bytes/HBM via int5 / int4 W4A16 conversion so the weight GEMM moves less data, and (ii) raise accepted-token parallelism and draft acceptance further on the decode side. Because (i) changes output distribution, it is guarded by a quality A/B acceptance gate. This report presents the standing throughput result, the quality evidence, and the concrete experiment matrix currently addressed to the 3000 target.

3  Methodology

3.1  Task and setting

  • Offline decode, Greedy (temperature=0), top_p=1.0, deterministic.
  • True S2 setting: output_len=max_tokens=8192, max_model_len=24576, FP8-Marlin, CUDA-graphs, max_num_seqs=128, max_num_batched_tokens=16384, gpu_mem_util=0.95, chunked prefill, prefix caching.
  • 1000-prompt dataset sc1_delta_v2.jsonl, reps=3, from the datastore; results persisted to shares/users/zxy/autobench/results. Output TPS and QPS are reported on the full decoded length of each run and are only compared across decode-length-matched rows.

3.2  Draft-swap protocol

  • Identical stack/batch/greedy; only the draft changes (assistant_model_path resolution).
  • DSpark b16 k=7, dspark_draft_topk=64; draft staged on the datastore, resolved at runtime.
  • Comparison honors a strict decode-length-matched rule: QPS and output TPS are only comparable at equal output tokens/request, otherwise the shorter decode looks artificially faster.

3.3  Quality A/B (weight-precision gate)

  • Reusable run_quality.py / run_quality_agentic.py score any branch/config via reserved _agentic_eval_* config keys (opt-in; the no-eval path stays byte-identical).
  • General tasks GSM8K + BBH; agentic multi-turn tool-loop (52 records); greedy, matched truncate + scoring path on both arms.
  • Acceptance: candidate (int5 now, int4 later) within noise of the FP8 control (<1–2% abs / 1–2 σ per benchmark).

Current best is 2634.58 output TPS (DSpark b16, true S2, 8192 decode). 3000 is a ~+14% step. The campaign treats this not as one change but as a stacked set of orthogonal, individually gated levers, so each contributes a measurable delta and none can silently regress quality:

6  Discussion

  • Method differences. DSpark b16 (a 5-layer qwen3 draft keyed on target hidden states, k=7, topk=64) materially raises accepted-token throughput over MTP k5 at an equal decode length (+3.8% @768).
  • Evaluation-harness artifact. The apparent "MTP control faster" reading is an artifact of its shorter decode (~1323 vs ~2291 tok/req) — the length-matching rule (Sec 3.2) excludes it as a comparator.
  • Road to 3000. The weight-HBM-bound Marlin GEMM (~53% of step time) is attacked on two fronts: precision (L1/L2 — int5 then int4 W4A16, quality-gated) and decode-side acceptance/parallelism (L3/L4, length-matched). None of these has landed end-to-end yet; L1 is in flight now. Datastore/mount specifics (identity-twin copilotexplore_dtalake_id vs SAS 403) are covered in the repo (Section 7).

7  Limitations

  • The clean 8192-length fractional delta vs MTP is not yet measured (control decoded short); a matched control is a pending comparator before we can attribute the 3000 gap with confidence.
  • Crossing 2500 is demonstrated; 3000 is a target, not yet a result. The L1–L5 deltas are hypotheses to be measured; no fabricated or extrapolated throughput is reported.
  • Throughput is offline single-worker; online batching/QPS at production concurrency is out of scope here.
