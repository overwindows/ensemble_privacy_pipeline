DLIS Falcon Qwen3.5-9B Freshness Serving Optimization: Eliminating Host-Side & Batching Bottlenecks for 2.31×–3.81× Production HTTP Throughput on A100

Chen Wu · Production Container cliff-freshness-dlis-falcon:20261021-v2 on AML Singularity.ND12am_A100_v4 · last updated 2026-11-13
Abstract. We present a systematic end-to-end performance diagnosis and optimization of the production DLIS Falcon Qwen3.5-9B CLIFF content-freshness HTTP model service (cliff-freshness-dlis-falcon:20261021-v2, entrypoint /model/start_freshness.sh http) on NVIDIA A100-SXM4-80GB. Using 1 Hz hardware telemetry and controlled ablations across both the official 120-prompt performance benchmark (input.performance.jsonl) and the 5-prompt heavy-truncation stress suite (input.json), we prove that unmodified production throughput is throttled NOT by GPU compute (SM activity sits at 52.7%–78.0%), but by three compounding host- and engine-level bottlenecks: (1) a single-request Tornado concurrency gate (_Parallelism_=1 → Semaphore(1)), (2) a conservative 4-sequence vLLM scheduler cap (VLLM_MAX_NUM_SEQS=4, max_num_batched_tokens=8320), and (3) a 17-step character binary search in freshness_prompt.py that executes up to 34 full ~8,000-token Jinja + HuggingFace tokenizer passes (~280–350 ms CPU time) while holding a process-wide mutex (self._tok_lock). We structure our solution into two 100% non-model (serving system & runtime) optimization tiers that require zero model retraining, zero checkpoint changes, and zero Docker image rebuilds: Tier 1 (Environment Variables Only, Zero Docker/Code Change) raises throughput from 16.96 → 31.81 QPS (+88%, 2.54× lower median latency) on the 120-prompt benchmark and 9.90 → 24.34 QPS (+146%, 2.46×) on the 5-prompt stress test. Tier 2 (Fast Single-Encode Binary Search + max_num_batched_tokens=32768, shippable via ADLS /Model drop-in or source patch with no Docker rebuild) preserves the exact binary-search truncation route while cutting per-step tokenization overhead by ~10× (even with request caching disabled: 37.87 QPS, +123% QPS & −36% p95 tail latency), reaching 39.18 QPS (2.31×) on the 120-prompt benchmark and 37.74 QPS (3.81×) on the 5-prompt suite while saturating the A100 to 93.3%–94.6% mean (100% median) SM utilization at 396 W / 400 W TDP.

1. Why Stock Prod Is Slow

GPU Is Starved on the Host Side (Only 53–78% SM Busy)

(a) Concurrency cap: Tornado defaults to _Parallelism_=1 and vLLM defaults to VLLM_MAX_NUM_SEQS=4.
(b) CPU lock stall: Overlong articles (>8,192 tokens) run a 17-step binary search under a global lock (self._tok_lock), calling Jinja + tokenizer 37 times (~280 ms) and blocking all other threads.

2. Tier 1: Zero-Code Config Win

Set 3 Env Vars → +88% to +146% QPS Immediately

Without touching a single file or Docker layer, setting _Parallelism_=32, VLLM_MAX_NUM_SEQS=32, and VLLM_GPU_MEMORY_UTILIZATION=0.90 lifts 120-prompt throughput from 16.96 → 31.81 QPS (+88%) and cuts c=32 median latency from 1,890 ms → 743 ms (2.54× faster).

3. Tier 2: Fast Binary Search

Single-Encode Truncation → 39.18 QPS & 100% Identical Output

Keeping the exact 75% head + 25% tail truncation boundary while computing the constant 5-token assistant delta once cuts binary-search tokenizations from 37 → 19 (~10× less locked CPU work), reaching 37.87 QPS (no cache) / 39.18 QPS (Full Stack) with 100% bitwise-identical token IDs.

  1. Bottleneck 1 — Tornado Concurrency Gate & 4-Sequence Engine Cap (Parameter Config): In http_server.py, request admission is gated by utils.get_parallelism(1) where _Parallelism_ defaults to 1. Meanwhile, model.py:224–225 defaults to VLLM_MAX_NUM_SEQS="4" and VLLM_GPU_MEMORY_UTILIZATION="0.80". Even under 32–64 concurrent callers, vLLM's V1 continuous-batching scheduler is starved to at most 4 in-flight sequences.
  2. Bottleneck 2 — Global self._tok_lock + 37-Pass Binary Search in freshness_prompt.py (Code Bottleneck): In model.py:307, every incoming request acquires a single global lock (with self._tok_lock:) before calling prepare_request(). Inside freshness_prompt.py:truncate_content_to_fit(), whenever an article's prompt exceeds max_length = 8192 tokens, the server middle-truncates Content via a 17-iteration binary search over kept_chars ∈ [0, len(content)], keeping head_chars = round(kept_chars * 0.75) from the start and tail_chars = kept_chars - head_chars (25%) from the end around \n...[truncated]...\n.
    Why the stock binary search takes ~280–350 ms of locked CPU time per overlong article: Inside encode_messages(), every single binary-search check executes: (a) tokenizer.apply_chat_template(..., add_generation_prompt=True) + tokenizer() for the prompt, and (b) a second tokenizer.apply_chat_template(..., add_generation_prompt=False) + tokenizer() with dummy assistant message {"role": "assistant", "content": "{}"} just to measure len(full_ids)—which is always a constant +5 tokens ({}\n<|im_end|>\n). Across initial check + kept=0 check + 17 loop iterations + post-loop re-encode, one overlong article triggers 37 full ~8,000-token Jinja + Rust tokenizer passes (~280–350 ms) while holding self._tok_lock, stalling all other Tornado threads.
  3. Bottleneck 3 — Hardcoded max_num_batched_tokens = 8320 in model.py (Code Hardcode): In model.py:234, max_num_batched_tokens=8320 is hardcoded to a single sequence's max context length without reading an environment variable. Under concurrent ~3,600-token prefills, an 8,320-token per-step budget caps each scheduler step at ~2 uncached prompts instead of batching 4–8 prefills + active decodes in a single GPU forward pass.

3  Two-Tier Optimization Design & Zero-Accuracy-Impact Guarantee

To decouple zero-code operational wins from container code patches—and to preserve the model author's exact 75% head + 25% tail middle-truncation binary search—we separate the optimization into three clean changes across two deployment tiers:

6  Workload Physics: Prefix-Cached vs. 100% Uncached Prefill Ceiling (perftest_gpu_saturate.py)

A critical question in evaluating LLM serving benchmarks is the role of Automatic Prefix Caching (APC, enable_prefix_caching=True), which vLLM 0.31 enables by default in hybrid 528-token Attention+Mamba alignment blocks:

  • Why APC is genuinely active in live online production: Every CLIFF freshness query prepends the static ~1,800-token system rubric (/Model/prompt.txt) before the article payload (~1,500–2,000 tokens average). In online production, the ~1,800-token system prompt is 100% prefix-cached across every request on the pod, and breaking-news articles scored multiple times across feed requests also hit the 65–74 GiB KV+Mamba cache (~158,000-token capacity on A100-80GB).
  • Measuring the 0%-cache worst case (enable_prefix_caching=False + 4-token per-request content salt): To establish the absolute physical floor when 0% of tokens hit cache (not even the system prompt), perftest_gpu_saturate.py disables prefix caching and mutates 4 interior tokens near the start of every request so every query executes a full uncached ~3,372-token prefill + ~7-token decode directly on AsyncLLM:
