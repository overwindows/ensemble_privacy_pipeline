An LLM-Driven Feed Recommendation System, Built from First Principles (No Training Required)

Chen Wu — MSN Feed Ranking
Design preprint · LLM = DeepSeek (deepseek-v4-flash, DLIS route family recohelper…CallDLIS/HotColdStartHPF) · no model training at this stage · updated 2026-10-16
Abstract  Today's MSN Feed ranking is a high-volume DNN funnel (Recall → L2 pre-select → L3 re-rank → L4/WPO) with the LLM reserved for quality gates and, experimentally, narrow re-ranking. This paper asks the inverse question from first principles: if you treat the LLM as the design center rather than an additive layer, what should the architecture be — and what can be built with zero training using DeepSeek? We derive a decision-function framing (rank = score a candidate given a user-context and a corpus) and show where a generic, instruction-following LLM is genuinely superior: semantic/intent understanding, top-K re-ranking and candidate composition, and explainability. We then split the problem into steps — content understanding, user understanding, retrieval, volume ranking, top-K re-rank & composition, and a deterministic quality gate — and assign each to the cheapest component that is provably sufficient (vectors/ML for scale, LLM for judgment). We present a hybrid lane design (A: LLM-as-feature-extractor vs B: LLM-as-top-K-re-ranker), the DeepSeek prompt contracts, the per-stage latency budget against the ~300 ms p50 end-to-end guardrail, and a stub repo layout. Nothing here requires training a new model; every ML surface is replaced by off-the-shelf embeddings and a reranker, and every judgment surface by a prompt.
Keywords:  LLM-driven recommendation · DeepSeek · top-K re-ranking · retrieval-augmented recommendation · hybrid ranker · explainability · no-training design · GenRec vs LLM-as-reasoner

1.Introduction & problem framing

A recommender picks, for a user-context u and a candidate corpus C, the top k items, i.e. it implements a ranking decision function rank(u, c) → score over items c ∈ C. The entire field is a question of where that score comes from. A pure DNN stack learns a fixed committee of interaction signals (impression / click / dwell / like = the "explicit + implicit feedback" path) and scales to 180K RPS, but it generalizes poorly to cold items, cannot read free-text intent, and cannot say why. A pure LLM can reason about any text but is too slow and too expensive to score every candidate at volume.

The design principle this paper uses: assign each sub-problem to the cheapest component that is provably sufficient. Vectors and an ML ranker win when the decision needs scale and statistical interaction signals; the LLM wins when the decision needs language understanding, judgment over a small set, or explanation. Concretely: the LLM (DeepSeek) is used offline to build a semantic content/user layer, and online only at the head of the funnel — re-ranking the top few dozen already cheaply-selected candidates and composing them into a coherent slate.

2.Why not all-LLM

Ranking every candidate with an LLM fails on three axes simultaneously (Table 1):

Table 1 —  Why a pure-LLM ranker cannot carry the funnel

AxisWhy the LLM losesMitigation used here
ScaleCorpus far exceeds what an LLM can score in budget; latency per token × candidates is prohibitive.LLM sees only the top-K head (≤48 candidates); vectors carry the tail.
Interaction statsLLM cannot natively ingest billions of implicit feedback events; that signal lives in log-sparse ML.ML ranker absorbs CTR/dwell; LLM refines that shortlist.
CostPer-request LLM scoring at 180K RPS is unaffordable.One short LLM call per request, cached where possible.
Corollary. The LLM is a judgment component at the head, not a replacement for the recall/volume tiers. This is exactly the LLM-as-reasoner (hybrid) paradigm, contrasted with Generative Recommendation in §4.

3.Step split — where the LLM wins

Decompose ranking into six steps and score each by "cheapest sufficient engine" (Table 2). The LLM-wins cells are language- or judgment-heavy and limited to a small candidate set; the ML/vector-wins cells are scale- or statistic-heavy.

Table 2 —  Step-level engine assignment

#StepWinning engineWhy
1Content understanding (item → semantic + extraction)LLM, offlineReads title/body/entities, emits tags+embeddings; one batch job; embeddings are cached.
2User understanding (ctx → long/short-term interest)LLM, offline/periodicInterest graph (MAI-Profile style) from history; refreshed daily, not per-request.
3Retrieval (billions → a few hundred)Vectors (off-the-shelf embedder)Top-k ANN by embedding similarity; pure scale.
4Volume ranking (hundreds → ~48)ML ranker (static/cheap)CTR/dwell interaction stats, freshness, diversity; sub-millisecond scoring.
5Top-K re-rank + composition (48 → 10–20)LLM, onlineSemantic relevance to free-text intent; dedupe/coherence/ordering of the slate.
6Quality + business gateDeterministic rules + SLMBlock unsafe/low-quality/gray content; no latency budget for judgment here beyond a cheap pass.
Key insight. Steps 1–2 convert document and user text into a durable, cached vector layer; steps 3–4 do the brute-force selection; step 5 is the only place an LLM scores against a live, user-specific goal — and only for ≤48 candidates so it fits the latency budget. Step 6 stays deterministic to guarantee safety.

4.Two paradigms: LLM-as-reasoner vs Generative Recommendation

There are two ways to make an LLM the "design center." Table 3 contrasts them so the choice is explicit.

Table 3 —  Two LLM-centric paradigms

DimensionA. LLM-as-reasoner (hybrid)B. Generative Recommendation (GenRec)
What LLM doesRe-ranks / composes a shortlist from a cheap rankerAutoregressively generates the next-item sequence (HSTU / HLLM / Woodformer-GenRec)
Training neededNone — off-the-shelf embed + reranker + prompted DeepSeekHeavy — train a next-item transformer on billions of sessions (GenRec uses 800+ A100)
GuaranteesExplainable decisions; stable; easy to A/BStrong on dense-signal sessions; opaque; brittle to cold users
Fit to this stage✓ Recommended (no training)✗ Out of scope until later

For the explicit "no training" constraint we standardize on Paradigm A. GenRec is listed as the long-horizon successor once interaction data and training budget permit.

5.Reference architecture

1 Content understanding (LLM/offline) 3 Vector retrieval (ANN) 4 Volume rank (ML → 48) 5 Top-K re-rank + compose (DeepSeek, online) 6 Quality gate (rules + SLM)

Stage 1 (offline, batched). For every in-scope item, a DeepSeek batch job emits: a 2–3 sentence structured summary, an entity/topic set, intent tags (e.g. ["breaking", "finance", "tutorial"]), and an embedding via an off-the-shelf encoder. Cached in a vector DB; refreshed on an ingestion schedule.

Stage 2 (periodic, cached). A per-user interest profile (long-term + rolling short-term window) is derived with DeepSeek from the user's reading history — the free-form, no-training analogue of MAI Profile's delta-window / decay design (§5.6 of the Profile DAG), stored as a compact interest-vector + tag list.

Stage 3 (per-request, vectors). Embed the user's current context (query / recent clicks) and run ANN retrieval over the item index to a few hundred candidates.

Stage 4 (per-request, ML). A stateless ranker (e.g. a lightweight GBDT-style or fine-tuned-foundation reranker) scores the few hundred by interaction signal + freshness + diversity and keeps the top ~48.

Stage 5 (per-request, DeepSeek — the core of this design). The top-48 shortlist, the user profile, and the task contract in §6 are sent to DeepSeek as one scored re-rank + composition call. It returns a globally-ordered, de-duplicated, diversified slate of 10–20; optionally with a one-line reason per item (the explainability win).

Stage 6 (guardrail). Deterministic filters (NSFW, gray-trait SLM for quality, business rules) run after re-rank; anything that fails is demoted/replaced. This guarantees safety independent of the LLM.

6.Prompt contracts (DeepSeek)

The online re-ranker (§5 Stage 5) is the contract that matters. Draft contract below — single call, strict output schema, per-item score + reason.

SYSTEM You are a feed-ranking editor. Given a user interest profile and a REL ranking of candidate items, re-rank a shortlist into the best coherent slate. Preserve informative diversity, avoid near-duplicate stories, and prefer items matching the user's explicit current intent. Return JSON. USER User profile (interest tags + level): {{profile}} Current intent / recent clicks: {{intent}} Candidates (REL rank, id, title, summary, tags, engagement): {{shortlist | json}} TASK 1. Score each candidate 0–100 for relevance to the user given profile + intent. 2. De-duplicate: if two candidates cover the same story, keep the higher-scoring one. 3. Order into a final slate of up to {{k}} items that reads well as a whole. 4. For each kept item: reason (≤ 12 words). OUTPUT (JSON only, no prose) {"slate":[{"id":"...","score":88,"reason":"..."}],"dropped":["id", ...]}

Table 4 —  Contract requirements and failure modes

RequirementAnchoringFailure mode if violated
Strict JSON, keys fixedExplicit output block + schemaUnparseable output → fall back to REL order (report rate)
Input capped (≤48 items, truncated summaries)Tight char budget per itemOversized prompt → latency/TTFT blowout
Scores on a fixed 0–100 scalePrompt states the scaleCross-request scale drift → mis-ranking
Determinism handled at runtimetemperature=0 + seedFlapping slate between identical requests

7.Latency budget

Table 5 —  Per-request p50 budget vs ~300 ms end-to-end guardrail

4 Volume rank~5 msstateless, sub-ms/item

Overhead / network~40 msserialization, hop
Total~275 mswithin the ~300 ms p50 guardrail
Design lever. The budget is dominated by one DeepSeek call. If p95 slips, (a) shrink the shortlist (48 → 24), (b) truncate per-item summaries harder, or (c) enable a streaming / cached-prefix path. Never spend LLM budget on stages 3–4.

Nothing in this layout trains a model. The only real callable today is toprank/caller.py against the existing DeepSeek DLIS route; everything else is an interface you can mock for a first end-to-end smoke test.

9.Evaluation rails

Because there is no training, "validation" means measuring system behavior, not model loss. Three rails:

Table 6 —  Three evaluation rails

RailWhat it measuresInstrument
1 OfflineRanking quality on logged impressions (NDCG/MAP/recall@K) with the LLM re-ranker in the loopReplay a day of logs; compare vs production span
2 AI judgeRelevance / coherence of the composed slate at scaleDeepSeek-as-judge scores the slate (the FARE-style GPT-based relevance judge)
3 Online A/BReal CTR / dwell / long-term engagement, latency, error rateShadow-traffic first, then A/B; guardrail = no regression on p50/p95/QoS

10.Staging and risks

Staging. (1) Stand up toprank/ against the real DeepSeek DLIS route and run the offline replay rail to see whether LLM re-rank > ML-baseline on logged data. (2) Optionally toggle stage-5 on top of a portion of live traffic behind a flag. (3) Only if gains hold, broaden. This keeps the no-training system deployable in days, not months.
