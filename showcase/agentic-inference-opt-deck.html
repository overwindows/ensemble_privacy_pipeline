DIMENSION 01
Optimization Perspective · The 4-Layer Serving Stack

Multi-Layer Co-Optimization

GPU inference throughput and latency are determined by the interaction of Application, Service, Engine, and Kernel layers. Optimizing any single layer in isolation hits a local ceiling—or even regresses the whole system when combined naively.

Layer 1 · Application Layer 2 · Service Layer 3 · Engine Layer 4 · Kernel
Dimension 1 · Optimization Perspective

The 4-Layer GPU Inference Optimization Stack

Every request traverses four layers from business payload to SM warp execution. Each layer exposes distinct, compounding levers.

Layer 1 · Top
Application Layer
Workload & payload shaping before tokens hit the server: disable unused reasoning trace (enable_thinking: false), bound output length & enforce json_schema constrained decoding, strip vision tower weights (--language-model-only) on text tasks, and eliminate redundant prompt binary-search re-tokenizations (37 → 19 calls).
Frees KV & HBM headroom; cuts CPU pre-processing & wasted output tokens
Layer 2 · Orchestration
Service Layer
Client/server traffic & serving gateway orchestration: concurrency window matching (c=64..128), pre-traffic compilation & CUDA-graph warmup gates, DLIS / Falcon MaxBatchSize alignment, and workload-aware prefix caching policy (enabling on high-hit templates vs disabling on unique-article streams to avoid Mamba block-size inflation 16 → 288).
Eliminates cold-start stalls, gateway bottlenecks & cache-alignment waste
Layer 3 · Runtime
Engine Layer
vLLM / vllm-msn runtime scheduling & speculative execution: chunked prefill overlap, joint tuning of --max-num-seqs & --max-num-batched-tokens (8K → 16K/32K), native Multi-Token Prediction (MTP k=3) & trained DSpark draft models (k=7, topk=64), and FULL_DECODE_ONLY CUDA Graph capture across speculative steps.
Maximizes decode batch density & accepts 3.3+ tokens per target forward
Layer 4 · Hardware
Kernel Layer
GPU architecture-matched CUDA / Triton kernels: FP8-Marlin MoE decode-2D tile/stage/warp geometry reshaping on A100, custom C++ CUDA fused chunk_gated_delta_rule MTP mixed-speculative kernels for Qwen3.5 hybrid GDN layers, FlashInfer vs Triton attention dispatch, and fast top-k greedy rejection-sampling kernels.
+17.5% from MoE kernel geometry alone; removes Python/Triton launch gaps
Dimension 1 · Top-Down Levers

Application Layer & Service Layer: shape the work before the GPU

Layer 1 · Application Layer Levers
  • Modality & Weight Stripping (--language-model-only): For text-only production pipelines (MAI Profile, GEM, Feeds Quality) served by multimodal backbones (Gemma-4, Qwen3.5), skipping vision encoders frees gigabytes of A100 HBM directly into KV cache capacity.
  • Reasoning & Schema Discipline: Explicitly gating thinking mode (enable_thinking: false) and binding xgrammar response_format: json_schema prevents runaway reasoning chains while guaranteeing 100% valid structured JSON.
  • Prompt Truncation & Tokenization Caching: In CLIFF freshness serving, replacing 18 repeated apply_chat_template calls inside binary search with a single pre-tokenized prefix/suffix splice cut CPU tokenization calls by 49% (37 → 19) with 100% bitwise-identical token IDs.
Layer 2 · Service Layer Levers
  • Workload-Aware Prefix Caching Policy: Prefix caching helps shared-system-prompt workloads, but on Qwen3.5 hybrid GDN+Attention with unique long prompts (~3,000 tok), enabling APC forces Mamba state alignment to inflate KV block size from 16 → 288 tokens. Turning --no-enable-prefix-caching eliminated fragmentation and boosted throughput.
  • Concurrency Window & Gateway Batching: Aligning client concurrency (c=8..128) and DLIS/Falcon MaxBatchSize with the engine's decode sweet spot keeps GPU SMs saturated without queueing tail-latency spikes.
  • Deterministic Pre-Traffic Warmup: Warming up Triton JIT caches, FlashInfer workspace buffers, and CUDA Graph pools across all batch sizes before opening traffic gates prevents first-wave timeouts.
Key Insight: Application and Service layers often yield the fastest, lowest-risk wins (up to 2.3× QPS on CLIFF and massive KV memory recovery on Qwen3.5/Gemma-4) while reshaping the batch profile that Engine and Kernel layers must execute.
Dimension 1 · Bottom-Up Levers

Engine Layer & Kernel Layer: maximize tokens per GPU cycle

Layer 3 · Engine Layer Levers (vLLM / vllm-msn)
  • Chunked Prefill & Token Budget Co-Tuning: Co-tuning --max-num-batched-tokens (16,384 / 32,768) and --max-num-seqs (128) overlaps prefill chunks with active decode steps, preventing prefill starvation on 3K-token prompts.
  • Speculative Decoding — Native MTP & Trained DSpark:
    • Qwen3.5-27B Native MTP (k=3): achieves 76.64% draft acceptance (mean accept length 3.30 tokens/step) across 2,000 production requests.
    • Gemma-4 Trained DSpark Draft (k=7, topk=64): compact target-hidden-state-conditioned draft replaces generic assistant draft (+28.8% total TPS).
  • Full-Decode CUDA Graph Capture: Capturing both target verification and multi-step draft execution under FULL_DECODE_ONLY eliminates Python dispatch overhead.
Layer 4 · Kernel Layer Levers (CUDA / Triton / C++)
  • FP8-Marlin MoE Decode-2D Geometry (Gemma-4): Reshaping tile / stage / warp config specifically for the small-batch MoE decode regime delivered a training-free +17.5% throughput jump (2,045 → 2,403.18 tok/s).
  • Fused C++ CUDA GDN MTP Kernel (Qwen3.5): Custom chunk_gated_delta_rule C++ CUDA kernel handles mixed speculative query-length batches (q_len = 1 + k = 4) natively in recurrent linear-attention layers.
  • Architecture-Aware Attention & Sampling Kernels: Rigorous A/B benchmarking on A100 (sm80) proved Triton GDN outperformed a backported FlashInfer sm80 prefill kernel (4.37 vs 3.79 QPS on decode-bound workloads)—preventing negative ports while adopting fast fused top-k greedy rejection sampling.
Why Engine + Kernel Must Be Co-Designed: Speculative decoding (k=3..7) changes the inner decode batch dimension from B×1 to B×(1+k). Kernel tile geometry and GDN recurrent state updates must be tuned specifically for that speculative verification shape.
Dimension 1 · The Core Principle

Co-engineer across all 4 layers → Global Optimum (not naive sum)

Two ways to optimize the 4-layer stack on the same GPU. Isolated layer tuning creates conflicts; cross-layer co-engineering compounds gains.

✕ The Trap — Tune layers in isolation, then stack
App/Service: enable prefix cache blindly → inflates Mamba block size 16→288
Engine: add speculative draft (k=7) → multiplies active token batch 8×
Kernel: tile geometry tuned for B×1 decode → thrashing & register spill at B×8
Local optima collide. Each layer looks optimal in a micro-benchmark, but stacked together they fight over HBM blocks, SM registers, and batch budgets.
Sub-additive or net regression
VS
✓ Our Approach — Co-engineer the 4 layers to one objective
App + Service: strip vision weights + set cache policy to maximize KV blocks
Engine: size mnbt/mns & DSpark/MTP depth (k) to fit the freed KV headroom
Kernel: tune FP8-Marlin 2D geometry & fused GDN specifically for the speculative batch shape
Global optimum. All 4 layers trade off parameters explicitly against end-to-end production TPS, QPS, TPOT, and quality gates.
Gemma4: 2,635 tok/s · Qwen3.5: 3,880 tok/s · CLIFF: 2.3× QPS

Why agentbus + Durable Memory Matter

Every role runs in its own isolated process/window and publishes structured state to agentbus. Kernel Dev sees Engine Evaluator's TPOT breakdown; Planner reads Memory so dead-ends are never re-run.
