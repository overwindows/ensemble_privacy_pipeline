Agentic Inference Optimization

Chen Wu · single NVIDIA A100 80GB (sm_80) · gemma-4-26B-A4B · vllm-msn fork
Abstract. How much more performance can we extract from one GPU — without changing the target model? On a single A100 80GB serving gemma-4-26B-A4B, we explore two complementary directions: (1) improving kernel execution geometry (a training-free lever) and (2) training a better speculative draft (a training-involved lever). The central idea is not either optimization in isolation, but the engineering loop connecting them — Propose → Research → Build or train → Run → Human acceptance criteria → Measure → Iterate. The selected geometry raised reported output throughput from 2045.0 → 2403.18 tokens/s (+17.5%, no training); combining that geometry with a trained DSpark draft reached 2634.58 tokens/s (+28.8% over the original baseline). The combined figure already includes both interventions. Throughput is reported; request-latency improvement is explicitly not yet evidenced (Sec 4).
Keywords: agentic engineering loop · speculative decoding · DSpark · MoE kernel geometry · A100

2  The Idea: One Loop, Two Vectors

The campaign is governed by a single repeated loop, applied to two very different optimization vectors:

Propose→ Research→ Build / train→ Run→ Acceptance criteria→ Measure→ Iterate
  • Vector 1 — improve how the system executes. Hypothesis: a weight-memory-bound decode could benefit from better execution geometry in the FP8-Marlin path. The agent explored tile sizes, pipeline stages, and warp settings; the selected configuration raised reported output throughput from 2045.0 to 2403.18 tokens/s — +17.5% without training. The target model stayed unchanged; the gain came from how the system executed it.
  • Vector 2 — improve what the system proposes. A different lever: raise the number of proposed tokens accepted per speculative-decoding step. This step trains a compact DSpark draft (keyed on the target's hidden states) to replace the bundled assistant while preserving the target model. With the tuned geometry, the DSpark configuration reached 2634.58 output tokens/s vs 2434.38 for the MTP-assistant configuration — a reported +8.2% raw throughput in that (non-length-matched) comparison (Sec 3.3).

Together, the selected geometry and the trained draft delivered +28.8% higher raw throughput than the original baseline, on the same single-GPU hardware. That combined figure already includes both interventions; it is not an additional gain to stack on top.

3  Method

3.1  Vector 1 — kernel execution geometry (training-free)

  • Single A100 80GB (sm_80), greedy (temperature=0), FP8-Marlin, CUDA-graphs, chunked prefill, prefix caching.
  • Change is confined to the MoE decode tile/stage geometry (a memory-pipelined "2D" decode schedule that overlaps attention and expert compute), selected by sweeping tile size, pipeline stages, and warp settings.
  • No weights change, no retraining — a pure inference scheduling win.

3.2  Vector 2 — trained DSpark draft

  • Train a compact general-purpose DSpark draft and deploy it on Gemma 4 in place of the bundled MTP-assistant draft (num_speculative_tokens=7, topk=64). Draft-only swap — the target's text_only/ weights are untouched.
  • Checkpoint staged at shares/users/zxy/autobench/data/dspark_b16 (msn-dni-c09); public source IWRITECODE/gemma4-26b-a4b-dspark-b16.

3.3  Measurement discipline

  • Output TPS/QPS are reported on the full decoded length of each run and only compared across decode-length-matched rows where stated.
  • Higher throughput is useful evidence but does not automatically establish lower request latency: equal configured token limits can still produce different actual output lengths. A latency conclusion would require TTFT, time-per-output-token, and end-to-end measurements — not included in the available campaign material, so latency improvement remains unverified.

5  Discussion

  • Two orthogonally different levers. Vector 1 is a pure inference/scheduling optimization (no training); Vector 2 is training-involved (a small draft). Both leave the served target model unchanged, so served-model quality is governed by the same greedy decode.
  • The loop, not the individual result, is the transferable outcome. Automated research + experimentation, targeted training where useful, and human judgment defining what counts as an acceptable result — applied around a single GPU.
  • Framing discipline. Throughput ≠ latency. Where the material doesn't support a claim, the page says so rather than extrapolating.
