2  Introduction

This campaign's story is 3776.67 → 3786.84 (reproduced baseline) → 5000 (target) — one model, one A100, and a methodical search over speculative-decoding levers. The reference 3776.67 came from a vL0.31 / FlashInfer / MTP k=3 recipe at full-2000 saturation; we first turned it into an owned, reproducible AML result, then probed whether scheduling caps or a smaller external DFlash draft could meaningfully beat it.

3  Methodology

3.1  Setup & harness

Measured on Singularity.ND12am_A100_v4 (1× A100 80GB, sm_80), vLLM 0.31.0, torch 2.13.0+cu130, via the frozen-stock harness (run_qwen_posted_eval, sitecustomize os-injection, tile32 OFF, admit_reused_cpu of image sha256:27ff34ae). Service profile: FLASHINFER main + TRITON draft, gpu_mem 0.9, bf16, no prefix cache, max-model-len 25600, max-num-seqs 128 / max-num-batched-tokens 16384. Throughput only (benchmark_enabled:true); exactness gates (tile32 OFF) held throughout.

3.2  Why full-2000 saturation matters

Prior cells ran sample=100, which under-saturates the server and reads a non-comparable 2453 output tok/s. The r9 reproduction runs the exact posted baseline on the full ~2000-prompt dev set (no subsample) so the server stays saturated and output_tps is directly comparable to the reference.

5  Discussion

Complete decomposition of the 1,156 tok/s cross-harness progression (`2,697.54 → 3,335.90 → 3,853.40`). Across Phase-2d, Phase-2e, and Phase-2f, we accounted for every token per second between the initial offline runner and r9: (i) +638.36 tok/s (+23.7%, Phase-2e) came from disabling thinking-mode output inflation (mean_out 2,252 → 1,287 tok/req, enable_thinking=False + greedy T=0.0) and forwarding FLASHINFER main + TRITON_ATTN draft + mamba_ssm_cache_dtype=bfloat16 + language_model_only=True; (ii) +517.50 tok/s (+15.5%, Phase-2f) came from upgrading the runtime from the v0.1.dev1 V1 fork (cudagraph_mode=PIECEWISE fallback + Triton GDN) to vLLM 0.31.0 V2 Model Runner (FULL_AND_PIECEWISE CUDA graphs + CUDA GDN decode kernel).

Why external DFlash lost while native MTP3 wins. At saturated batch concurrency (c=128), a 4-layer 1.71B external draft model adds full-layer weight reads and extra KV cache pressure every step, losing by 20–37% at k=7 and 33% even at k=3. Native MTP3 shares the backbone activations and runs a single lightweight head with 76.4% acceptance (3.29 tokens/step incl. bonus).

6  Limitations & Path to 4,000+

Limitations & Current Gap: With the Wave-6g 4-patch greedy champion stack (HTTP_V031_WAVE6G_GREEDY_MINIMAL_STACK_K3, magenta_book_0g0hp7t2cy), online HTTP /v1/chat/completions throughput on 1× A100-80GB is verified at 3,879.50 output tok/s (+92.66 tok/s / +2.45% over r9's 3,786.84 tok/s, 12,728.44 total tok/s, 3.01 QPS, 663.54s wall time, 2000/2000 = 100.00% JSON valid, and 4,040.4 tok/s steady-state median across full Running=128 decode windows) — leaving only 120.50 tok/s (+3.11%) of end-to-end ramp/drain amortization to cross 4,000+ output tok/s.

Remaining levers to clear 4,000+ end-to-end output tok/s (+3.11% over 3,879.50) on 1× A100-80GB:

  • C++-level mixed-batch GDN decode dispatch (zero Python tensor split) — Steady-state pure-decode intervals already sustain a 4,040.4 tok/s median, while the ~4,000 mixed prefill+decode steps pull the 2,000-request average down to 3,879.50 tok/s. Extending ops.fused_gdn_decode_post_conv_mtp in C++/CUDA to accept mixed batch index masks directly (without Python-level tensor slicing) targets the remaining ~120 tok/s gap.
  • Two-stage Markov candidate filtering for DSpark (`top-256` base → `top-64` Markov) — Wave-6h showed that pruning DSpark's Markov head to top-64 (`gray_drop_m1pb1vf7v9`, 3,695.43 tok/s) saves 500× Markov weight bandwidth but loses -1.49 pp acceptance when the bigram boost comes from ranks 65–256. Evaluating a wider top-256 or fused Triton top-k + Markov kernel preserves acceptance while keeping the 32k projection off the critical path.
  • Weight compression (for 4,200–5,000 stretch goal) — An offline W8A8 FP8 / INT8 SmoothQuant or W4A16 Marlin quantization of the 24 GDN + 8 full-attention target layers cuts per-step weight HBM traffic by 50–75% on the memory-bandwidth-bound A100 decode step.
