Under production stochastic sampling, the same L1–L4 DSpark k=5 configuration sets new records of 3,778.22 output tok/s at T=0.8, top_p=0.6 (bright_garage_ztnrp07r47, +122.27 tok/s / +3.34% vs stock 3,655.95, 100.0% valid JSON) and 3,765.50 output tok/s at T=0.6, top_p=0.8 (plucky_mangos_rqg5nnbmkq, +96.95 tok/s / +2.64% vs stock 3,668.55).

2.3  Manual Server Launch & DLIS `deployment-params.yml`

To apply the 4 patches manually and start vllm serve directly (or inside a DLIS Falcon container):

# Step 1: Apply the 4 pure-Python patches (<1s at container start, no C++ compilation)
VLLM_SITE_ROOT="$(python3 -c 'import os, vllm; print(os.path.dirname(os.path.dirname(os.path.abspath(vllm.__file__))))')"
patch -d "$VLLM_SITE_ROOT" -p1 --forward < vllm_v031_eagle_full_cudagraph.patch
patch -d "$VLLM_SITE_ROOT" -p1 --forward < vllm_v031_fast_spec_sample.patch

patch -d "$VLLM_SITE_ROOT" -p1 --forward < qwen35_d2g_v031.patch

# Step 2: Launch vLLM 0.31.0 online HTTP server
export OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 NUMEXPR_NUM_THREADS=1
export TOKENIZERS_PARALLELISM=false
export D2G_TILE=64 D2G_STAGES=2 D2G_WARPS=8

exec vllm serve "$MODEL_PATH" \
    --host 0.0.0.0 --port 8100 \
    --served-model-name maiprofile-qwen35-sft \
    --tensor-parallel-size 1 --data-parallel-size 1 \
    --max-model-len 25600 --gpu-memory-utilization 0.9 \
    --max-num-seqs 128 --max-num-batched-tokens 16384 \
    --dtype bfloat16 --trust-remote-code \
    --hf-overrides '{"architectures": ["Qwen3_5ForConditionalGeneration"]}' \
    --async-scheduling --no-enable-log-requests --disable-uvicorn-access-log \
    --mamba-ssm-cache-dtype bfloat16 --no-enable-prefix-caching \
    --attention-backend FLASHINFER --reasoning-parser qwen3 \
    --default-chat-template-kwargs '{"enable_thinking": false}' \
    --language-model-only \
    --speculative-config '{"method": "mtp", "num_speculative_tokens": 3, "attention_backend": "TRITON_ATTN"}'

4.1  Kernel, CUDA Graph & Sampling Optimizations on `vLLM 0.31.0`

We systematically profiled the vLLM 0.31.0 V2 GPU worker on 1× A100-80GB and evaluated every candidate kernel and graph optimization across full 2,000-request online HTTP runs:

  • Why vllm_v031_fast_spec_sample.patch saves 2.03 GB/step (+31.04 tok/s): In stock vLLM 0.31.0, RejectionSampler.forward unconditionally calls apply_sampling_params(..., logits.to(torch.float32)) on the [512, 248320] target vocabulary tensor (127.1M elements) and runs a separate _temperature_kernel before rejection_sample_kernel — even when no top_k, top_p < 1.0, or penalty processors are active and even though rejection_sample_kernel already supports inline apply_temperature. Passing BF16 logits zero-copy eliminates 2.03 GB/step (88%) of rejection-sampling HBM traffic. When requests specify top_p < 1.0 (e.g., production temperature=0.8, top_p=0.6), can_fuse_temperature automatically detects top_p != 1.0 and routes to standard apply_sampling_params nucleus filtering with zero config changes.
  • Why vllm_v031_eagle_full_cudagraph.patch unlocks draft FULL_DECODE_ONLY CUDA graphs (+34.34 tok/s combined 3-patch greedy / +31.26 tok/s isolated on DSpark): Because the target model uses FLASHINFER alongside 24 Mamba/GDN layers, vLLM downgrades top-level cudagraph_mode to PIECEWISE. Stock AutoRegressiveSpeculator.set_cudagraph_mode only enables FULL_DECODE_ONLY when the target's decode mode is FULL, forcing all 3 MTP draft decode steps to execute piecewise through Python. Decoupling the draft check when draft_attn_backend == "TRITON_ATTN" captures all 3 draft steps into a single CUDA graph per batch size.
  • Why 2-hunk vllm_v031_gdn_minimal.patch beat the 4-hunk Python mixed-batch split (+2.04 tok/s vs. -63.15 tok/s): During the ~4,000 mixed prefill+decode steps, splitting decode and prefill tokens in Python adds 264 extra CUDA kernel launches per step (torch.index_select + index_copy_ across 24 GDN layers), costing more CPU/launch latency than it saves on GPU (sleepy_neck_v2dklhrnl4 dropped to 3,814.31 tok/s). Keeping only the zero-overhead torch.zeros → torch.empty fix on the fused C++ GDN decode path lifted the 3-patch stack from 3,877.46 to 3,879.50 output tok/s.
  • Why Native MTP k=3 beats k=4 (+132.51 tok/s): Increasing speculative depth from k=3 to k=4 (joyful_root_cy8y5xk25m) adds a 4th draft step with marginal acceptance (0.556 on position 3, lowering overall acceptance from 76.64% → 71.13%) and swells the target verification batch from 4N=512 to 5N=640 tokens/step (+25% target FLA/attention compute), dropping throughput from 3,879.50 to 3,746.99 tok/s.

6.2  Sampling-Decoding Optimization Analysis (Wave 6m/6n v1 vs. Wave 6o v2)

Why did vllm_v031_compact_topk_resample.patch v1 regress throughput by -20 to -38 tok/s in Wave 6m/6n, whereas v2 (Wave 6o) lifts T=0.6, top_p=0.8 by +57.08 tok/s over v1 to a new stochastic record of 3,687.48 tok/s?

  1. Why v1 regressed: In speculative decoding with k=3, each request produces k+1 = 4 logit rows (512 rows across B=128), of which _verify_kernel accepts 0..3 tokens and at most 1 row per request (1×B = 128 rows) is ever resampled/bonus-sampled by _resample_kernel. Running pre-verification stream compaction across all 4×B×248,320 logits required 4 dynamic PyTorch tensor allocations and 2 extra kernel launches per verify step, costing more HBM bandwidth than the 1×B resample saved.
  2. How v2 (Wave 6o) eliminates all allocations and skips >98% of _resample_kernel work in-place:
    • Zero-cost block-max reuse: Stock _compute_local_logits_stats_kernel already splits the 248,320 vocabulary into 31 blocks of 8,192 tokens and computes target_local_max after _topk_topp_kernel has masked all rejected tokens to -inf, but previously skipped bonus-token rows (draft_step_idx ≥ k). Enabling target_local_max on bonus rows when temp ≠ 0.0 provides an exact 8,192-token non-empty mask at zero extra kernel launches.
    • Two-level masked-block short-circuit in _resample_kernel: Each of the 243 CTA blocks per sequence (1,024 tokens/CTA) first checks parent_max = target_local_max[row, block_idx // 8] (1 scalar FP32 read). Since top_p ≤ 0.8 leaves only 1–32 surviving tokens out of 248,320, 29–30 of the 31 parent blocks are -inf and exit immediately without touching the 248,320-wide target_logits or draft_logits tensors. Within the 1–2 surviving 8,192-token parent blocks, a Level-2 check tests tl.max(target_logits) == -inf on the 1,024-token tile and exits before reading draft_logits, evaluating tl.exp/log1p, or running 4-round Murmur3 Gumbel PRNG.
    • Same short-circuit in _compute_local_residual_mass_kernel and gumbel_noised_argmax: Skips all -inf blocks during residual mass integration and 1-token Gumbel sampling, plus pre-warms the 107 MB _TRITON_BUFFER_CACHE during server startup.
